# F061.2 — Bevis at upmetrics dedupper på vores idempotencyKey

## Hvorfor
F061.1 genforsøger en fejlet POST i baggrunden. Det er kun sikkert hvis upmetrics' `/api/agent` dedupper på `tags.idempotencyKey` — ellers tæller et genforsøg forbruget to gange. upmetrics siger det gør (F028.2, prod siden 8/9, #558). Vi vil se det svare fra deres database, ikke tage det på ord.

## Hvordan
En `workflow_dispatch`-workflow:
1. Enroll-trinnet kopieret ordret fra `broberg-ai/upmetrics/.github/workflows/upmetrics-enroll.yml` (OIDC, audience = upmetrics.org). Nøglen maskeres før brug og forlader aldrig jobbet. Fly-trinnet udeladt — ai-sdk har ingen Fly-app.
2. Smoke-trin: POST samme nyttelast to gange, derefter en tredje med ny nøgle. Assert med jq:
   - svar 2: `upserted == true` og `run_id == svar1.run_id`
   - svar 3 (negativ kontrol): `upserted == false` og `run_id != svar1.run_id`
3. Nyttelasten: `cost_usd 0`, alle tokens 0 (så upmetrics heller ikke udleder en pris, F027), `tags.smoke = "dedup"`.

## Forbehold (fra upmetrics)
Seneste body vinder ved upsert. Derfor skal nøglen være unik pr. logisk kald — vores er `randomUUID()` pr. nyttelast, aldrig afledt af indhold.

## Reuse
upmetrics' enroll-workflow (Discovery-kilden for enrollment) genbruges ordret; intet eget auth-flow.
